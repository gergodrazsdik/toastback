# 0018: Waiting for an answer: `--wait`, `wait ID`, and notify-send's `-w` and `-A`

- Status: accepted
- Date: 2026-11-26

## Context and problem statement

[0017](0017-notify-send.md) approved an opt-in wait: async stays the default, and a caller that asks can block
until the notification is answered. It left the design open: how the waiting process learns of the click (which
Windows hands to a new toastback process through `toastback://`), how a dismissed toast is noticed, the output and
exit codes (a public API), and Ctrl-C, since the caller usually runs in WSL and the waiting exe on Windows.

## Considered options

1. Learning of the click: a named pipe that the click process writes to, or the pending file that the click process
   already updates.
2. Noticing a dismissal: `ToastNotification.Dismissed` in the showing process, or asking Windows whether the toast
   is still in the notification center.
3. Output: only the answer, or the id and then the answer.
4. Exit codes: distinct codes for each ending, or 0 for all as notify-send does.
5. Ctrl-C: a console control handler only, or also watching the calling WSL process.

## Decision outcome

Chosen:

- **The pending file carries the answer** (option 1.2). `Store::claim`, which already marks a notification done
  atomically, records `answer`: the button id, `__body` for a click on the toast's text, or nothing when a dialog
  was closed without a choice. The waiting process reads the file every 200 ms. There's no second channel to set
  up or clean up, and `toastback wait ID` after the click still gets the answer.
- **Every click reaches toastback.** Before, a button with nothing to run was a Windows `system` "dismiss" button,
  and a toast with nothing to run on a text click had no `launch`, so Windows closed the toast without starting
  toastback, and a wait saw a dismissal. Every button and every toast's text now activate `toastback://`; the
  handler records the answer and runs nothing. A click like that costs a short, invisible process start, and is
  logged. Activating only when someone waits would leave `toastback wait ID` blind to toasts shown without
  `--wait`.
- **Dismissal: the toast leaves the notification center** (option 2.2). The waiting process asks Windows
  (`ToastNotificationHistory`) whether the toast is still there. A banner that times out moves into the center and
  stays; a toast the user dismisses doesn't. That works for `wait ID` from any process, which an event in the
  showing process wouldn't. A click also takes the toast out of the center, a moment before the click process has
  claimed it, so the toast counts as dismissed only once it has been gone, unclaimed, for 5 seconds, and not while
  a details dialog it opened is still open.
- **`--wait` prints only the answer** (option 3), so `choice=$(toastback --wait …)` needs no parsing. `--id` names
  the notification in advance when the caller needs the id too.
- **Distinct exit codes** (option 4): 0 answered (the answer is on stdout), 5 closed without a choice (dismissed, a
  dialog closed, removed, shown again under the same id), 6 timed out (`--timeout`, or the notification expired),
  130 interrupted. `wait` on an id with no notification exits 2. The codes of `show` don't change.
- **Ctrl-C** (option 5): a SIGINT in WSL never reaches the Windows process; tested, the waiting exe kept running.
  So the shim (v4) passes `--caller-pid $$`, its own process id, which `exec` keeps for WSL's interop relay, the
  process that Ctrl-C ends. Every second, the waiting exe checks `\\wsl.localhost\<distro>\proc\<pid>`, and stops
  once it's definitely gone (an error other than "not found" doesn't count). A console control handler covers
  `toastback-cli` in cmd and PowerShell. An interrupted wait leaves the toast, whose buttons still run their
  callbacks; notify-send removes it, as libnotify does on SIGINT.
- **notify-send**: `-A [NAME=]Text` is a button (at most 5), and `default` is a click on the toast's text. Unnamed
  actions are numbered from 1, as libnotify's code does. `-A` implies `-w`, and `-t` limits the wait. The chosen
  NAME is printed; a dismissal or another click prints nothing, a timeout prints "Wait timeout expired" to stderr,
  and every ending exits 0, as in notify-send. A critical toast gets its Dismiss button only when it has no other.
- **notify-send's file descriptors** (`--id-fd`, `--selected-action-fd`) belong to the Linux process, which the
  Windows exe can't reach. The wrapper (v2) handles them: when the arguments mention `-fd`, it passes
  `--toastback-records` first, the exe prints `out TEXT` and `fd N TEXT` lines, and the wrapper writes each to
  stdout or that descriptor, then exits with the exe's exit code. Without `-fd` it `exec`s as before. Called without
  the wrapper, these options exit 1. `--activation-token-fd` is accepted and gets nothing: Windows has no
  activation token.

### Consequences

- A dismissal is reported (exit 5) but still runs nothing: callbacks remain for clicks only.
- A wait polls a small file and the notification history; the cost is a few WinRT calls a second.
- A shim older than v4 passes no caller id, so after Ctrl-C its waiting exe runs until `--timeout` or the
  notification expires. `install` writes v4, and `doctor` reports older shims as outdated.
- A dismissal within 5 seconds of a click that never gets claimed (the click process failed to start) is reported
  as dismissed.

## More information

Found in manual testing: notify-send's `-A` buttons (which never have a `run`) were reported as dismissed when
clicked, until every click went through the handler. Tested live: a click through the protocol handler is the answer, `wait` after it returns the same answer, a toast
removed from the notification center behind the pending record's back is "dismissed" after the grace period, and
after a SIGINT to the shim no `toastback.exe` is left. Windows sees a WSL process's `/proc` entry through
`\\wsl.localhost` in about 25 ms.
